# App-level a11y gaps surfaced by `ui_aria_audit`

> Follow-up to `docs/plans/2026-05-11-aria-mcp-tools.md`. That plan shipped the dev MCP's seven `ui_aria_*` tools; the audit pass against the running app produced 27 findings on one view (Settings → Länkregler), with the same pattern likely repeated across every modal + form-driven view in the codebase. This plan addresses the app-side fixes the tool found.

## User goal

A user who navigates Släktforskning with a screen reader hears the same affordances a sighted user sees: every clickable has a name they can act on, every region they care about can be jumped to by name, every form input is announced with its label (not its placeholder), and the Settings tab strip is announced as tabs — not anonymous buttons. Today a screen-reader user opening the +Regel modal hears five "edit, blank" inputs in a row and can't tell which is which. They hear `<main>` as an unnamed landmark and can't jump to it by name. They hear "Länkregler, button, 3 of 11" instead of "Länkregler, tab, 3 of 4 selected". This plan closes those gaps.

The verification surface for this plan is exactly the dev MCP's `ui_aria_audit` — every finding fixed in this plan disappears from the audit's output. That's a mechanical, observable check; we don't have to argue about whether a fix is "enough."

## Scope

**Every finding-kind `ui_aria_audit` reports** on the running app at the time this plan starts. Listed in the order they showed up in the 2026-05-12 audit pass:

1. **`input_without_label` × many.** Every `<input>` / `<textarea>` / `<select>` whose accessible name comes only from placeholder/title or nothing at all. Concrete instances counted in the audit pass:
   - Aktiva regler table: 12 row-checkboxes (one "Aktiv" toggle per rule).
   - +Regel modal: 5 inputs (Namn, Mönster, URL-mall, Exempel, Prioritet).
   - Likely repeats across every modal in `src/renderer/components/modals/` and every list-row's inline checkbox.
2. **`unnamed_interactable` × many.** Subset of #1 above where the input has no name at all (not even a placeholder).
3. **`tab_strip_without_role` on the Settings tab strip.** The `<div>` containing the Databas / Standardval / Länkregler / Ortsregister chips uses `role="button"` on each chip. Should be `role="tablist"` on the container + `role="tab"` + `aria-selected="true|false"` on each chip + `aria-controls` pointing at the panel. Likely repeats in any other tab-shaped UI (chart-view tabs?, persons-view list/tree tabs?).
4. **`unnamed_landmark` on `<main>`.** The page's main content has no `aria-label`. Screen-reader users can't jump to it by name (`D` key in NVDA, `VO+U` in VoiceOver). Should carry an `aria-label` derived from the active route (e.g. "Inställningar", "Personer", "Platser"…). Likely best done in `App.vue` or each `*View.vue`'s root.
5. **Bonus: no `<h1>` on the page.** Not in the audit yet (the audit doesn't check heading hierarchy), but visible in `ui_aria_headings` output — every view starts at H2. Sighted users have the page title in the window chrome; screen-reader users typically expect an H1. Worth a follow-up audit-finding-kind (`missing_h1`) once we agree on the right level.

### Scope deviations

- **`positive_tabindex` and `disabled_focusable` finding kinds are NOT covered.** The 2026-05-12 audit found zero of those in the Settings view. They'll become in-scope only if a future audit surfaces them.
- **Heading-hierarchy issues (H2 → H4 skip in the Settings view) are NOT covered.** Out of scope; better as part of a "heading audit" follow-up that adds an `audit` finding-kind for it first.
- **Skip-link a11y is already correct.** "Hoppa till huvudinnehåll" appears first in the tab order, points to `#main-content`. No change.

## Verification

User-observable outcome: a screen-reader user opens the Settings view, hears "Settings landmark", uses the H key to navigate to "Länkregler" (H2), tabs into the tab strip and hears "Länkregler, tab, 3 of 4, selected", tabs into the +Regel button, opens the modal, tabs through Namn / Mönster / URL-mall / Exempel / Prioritet and hears each labelled correctly.

The mechanical check: `ui_aria_audit()` against the running app returns `{ findings: [], total: 0 }` for the Settings view after this plan ships. (Some `unnamed_interactable` findings may legitimately remain — e.g. an icon-only button with `aria-hidden="true"` on its glyph that fails our heuristic — but every finding must be either fixed or justified in code with a comment + an entry in a "known-acceptable" list this plan adds.)

1. **`ui_aria_audit()` on Settings → Länkregler returns 0 findings** (or a documented allow-list).
2. **`ui_aria_audit()` on every other view** (Persons, Platser, Media, Sök, Grupper, Uppgifter, Källor, Kvalitet, Dubbletter, Rapporter, Diagram, Webbplats, Import/Export, every modal opened from those views) is run and its findings audited. Each finding is either fixed or added to the allow-list with a one-line rationale.
3. **`ui_aria_landmarks()` returns `has_name: true` for every landmark** in the document on every route.
4. **`ui_aria_invoke({ name: 'Länkregler', role: 'tab' })` succeeds** (currently the role is 'button', so this throws no-match).
5. **A test added to `tests/components/` or `tests/unit/`** that boots every top-level view and asserts `ui_aria_audit` returns 0 findings (or only allow-listed kinds). Replaces ad-hoc per-PR auditing with CI enforcement.

## Failure modes / RCA reference

This plan exists because:

- **Three bugs that shipped to a v1.0.0-shaped app were invisible until the dev MCP's ARIA tools surfaced them.** Specifically: chip strip masquerading as tabs (shipped 2026-05-09 ish), `<main>` with no aria-label (shipped 2026-05-10 with the Tauri merge), modal inputs without label associations (shipped before the BaseSubPanel refactor in 2026-04). Each lived in CI-green code with no flag. The tool exists to make this class of bug noisy by default; this plan is the cleanup that bug-class never got.
- **WCAG-contrast tests already enforce color a11y in CI** (`tests/unit/wcagContrast.test.ts`). There is no equivalent for structural a11y (landmarks, names, roles, states). Adding the audit-driven test in Verification §5 closes that gap.

## Tasks

### Task 1: Settings chip strip → tablist pattern

- [ ] Find every `chip-btn` strip in `src/renderer/views/SettingsView.vue` and any sibling view that uses the same pattern. Likely also in `VisualizationView` (Stamtavla / Timglas / Efterkommande / Solfjäder / Tidslinje tabs) and `PersonsView` (Tree / List tabs).
- [ ] Refactor the container to `role="tablist"`, each chip to `role="tab"` + `aria-selected="true|false"` + `aria-controls="<panel-id>"`, and the corresponding content panel to `role="tabpanel"` + `aria-labelledby="<tab-id>"`.
- [ ] Keep the current chip-button visual styling; only the ARIA changes are required. Add a `tests/components/` test that asserts the tablist contract holds for at least one example.
- [ ] After the change, `ui_aria_list({ role: 'tab' })` on Settings should return four entries with `selected: true` on the active tab.

### Task 2: Modal form inputs → `<label for=>` associations

- [ ] Sweep every modal in `src/renderer/components/modals/`. For each `<input>` / `<textarea>` / `<select>` without a programmatically-associated label, add an `id` to the input and `for="<id>"` to its visible label. The labels are already there visually; only the association needs adding.
- [ ] Concrete first pass: the +Regel modal (5 inputs). After the fix, `ui_aria_audit({ region: 'Regel' })` returns 0 findings.
- [ ] Repeat for every `BaseSubPanel`-hosted form discovered in the broader audit pass (Verification §2).

### Task 3: Row-level checkboxes → accessible names

- [ ] The Aktiva regler table's 12 row-checkboxes need a per-row accessible name. Likely shape: `<input type="checkbox" aria-label="Aktiv: {{ rule.name }}">` or `<label class="sr-only" for="aktiv-{{ rule.id }}">Aktiv: {{ rule.name }}</label><input id="aktiv-{{ rule.id }}" type="checkbox">`.
- [ ] Same pattern applies to any other list-row inline checkbox (Quality view's "ignore", Duplicates view's pair selection, …). Audit those views and apply.

### Task 4: Named `<main>` per route

- [ ] In `App.vue` or the route guard, derive an `aria-label` for `<main>` from the current route's title (the same string the window chrome shows). Use the existing i18n keys.
- [ ] Verify with `ui_aria_landmarks()` on every top-level route: every entry has `has_name: true`.

### Task 5: CI enforcement test

- [ ] Add `tests/components/aria-audit-zero-findings.test.ts` (or similar). For each top-level route, mount the view in a happy-dom env (or boot the running app via the e2e harness — pick whichever is cheaper), run the same audit logic the dev MCP runs (the `runAriaQuery` function is already importable), assert `findings` is either empty or a subset of an allow-list maintained in the test file.
- [ ] The allow-list starts empty; entries get added only with a code comment in the offending file linking to a tracking issue + a sunset date. **Default behavior:** any new a11y gap fails CI.

### Task 6: Audit pass on every other view

- [ ] Walk every top-level route via `ui_aria_audit({ region: '...' })` or document-wide. For each finding, either fix immediately (small) or add it to this plan's "Tasks discovered during execution" with severity ranking. The audit is the source of truth.
